## ⛔ 零、最高优先级：绝不能碰风控

风控是**唯一会让整个功能不可用**的风险，而且开发当天已亲手触发**两次**。
症状：`104009` + `sip:[]`，持续数小时，vkey 全挂（歌单/登录/搜索照常）。

**三条红线，任何时候不得违反：**
1. ❌ **批量预热整个歌单**
2. ❌ **失败后自动重试循环**
3. ❌ **定时后台任务刷接口**

**必须实现的保护：**
- **熔断器**：连续 N 次 `104009` / `104604` → 停止所有解析 **15-30 分钟**，页面显示「音源暂时不可用」。
  继续重试只会延长封禁。**当天就是缺这个，从「试几次」变成「封几小时」。**
- `104604` 是官方的「操作过于频繁」码，可用于**精确触发**熔断。
- 限流：普通用户 30次/分；`canEditMapping` 更宽松。
- **危险的不是频率，是模式**：人工操作不规律=正常；脚本批量刷=异常。

**排查方法**：先用**匿名请求**打同一接口。匿名与带 cookie **症状相同 = IP 层问题**，
别去折腾 cookie 和参数（详见第六节）。

## 一、游戏侧（已实扫确认）

1. 游戏分两大环节：**歌P** 和 **唱卡**（唱卡含 两军对决 / 极限抢唱 / 对方出牌三选一）。
2. 唱卡三种玩法**处理上完全不区分** —— 都是「先一批歌名+歌手，演唱时给歌词」。
2b. **⚠️ 一批里的歌会被陆续唱掉，不是只唱一首**：
    先出一批(3-5首) → 演唱时从中选一首唱，**或者一首一首地选** → 每次演唱出歌词。
    → UI 上卡片要能标记「已唱过 / 正在唱」，不能假设一批只对应一次演唱。
3. 三套控件对应三个环节，靠 holder 前缀区分：

   | 环节 | holder 前缀 | 内容 |
   |---|---|---|
   | 选歌（3-5首） | `singerDuelPlayingHolder` | 歌名/歌手**分离**，带 selectedSeatNo |
   | 演唱中 | `singerDuelSingingAudienceHolder` | `歌名-歌手` 合并 + 歌词 + snippetStyle |
   | 歌P历史 | `singerDuelPrepareAndSingSingerWorksHolder` | `《歌名》` 滚动，只渲染3行 |

4. **选歌环节 5 首一次 dump 全拿到** → 「一批」天然完整，不用跨次累加。
5. 歌名歌手配对靠 **bounds 的 y 坐标**（歌名底边 == 歌手顶边），不靠出现顺序。
6. **批次指纹只用歌名+歌手，不含座位号** —— 座位号会变，含进去会把同一批判成新批。
7. 抓取双通道：选歌(3-5s，**可能漏**) + 演唱(25-30s，**必抓到，兜底**)。
8. ⚠️ 歌词有**三种**干扰，都要能容忍：
   - `snippetStyle = 歌词乱序` → 行**顺序被打乱且可能不连续**
   - **隐藏部分字，用 `_` 代替**（如 `我的青_ 也不是没伤_`）→ 当**通配符**处理
   - **错别字** —— 游戏系统本身的问题，不是故意设定 → 需模糊匹配（可用拼音兜底）
   → **绝不能整段匹配 LRC，必须逐行独立匹配 + 容错。**
   ⚠️ 注意：**歌词里的 `_` 是占位符，歌手名里的 `_` 是分隔符**，两个场景不能共用同一套处理（见第32条）。
9. 歌P那 6 首是**已唱历史**不是候选；本轮要唱的是 `ctv_targetSingerName` 给的指定歌手。

## 二、模式与连接

10. **模式由「用户在哪个页面」决定**，不做 APK 自动判断：
    打开 `/live` → 唱卡模式；歌单页点自动打标 → 歌P模式。
11. 好处：扫描范围减半、不可能误写脏数据、用户不需要模式开关。
12. **⚠️ 现有架构是「APK 短连接 POST + 浏览器 SSE」，APK 没有长连接。**
    → 所有关于 Android 保活 / Doze / okhttp-eventsource / 退避抖动的讨论**对"维持连接"不适用**。
12b. **但「防止 APK 被系统杀掉」仍然重要** —— APK 被杀 = **扫描停止**，那才是真问题。
    理由不是"保持连接"，而是"别被杀"。**应写进使用指南**，APK 里放个按钮跳转到设置页。
    权威资源 **dontkillmyapp.com**，各厂商路径：

    | 厂商 | 路径 |
    |---|---|
    | 华为 | 应用启动管理 → 关闭自动管理 → 允许自启动 |
    | 小米 | 授权管理 → 自启动管理 |
    | OPPO / vivo | 权限隐私 → 自启动管理；任务界面点**锁图标** |
    | 通用 | 设置 → 应用 → 电池 → 不优化 / 关闭「后台限制」|

    开发者侧：申请 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`（normal 权限，自动授予），
    用 Intent 直接跳到设置页引导用户。
13. 模式切换**不用新推送通道** —— APK 每次 POST heartbeat 都有响应，响应里带 mode 即可。
14. 配对 vs 连接是两回事：**配对一次永久有效**；连接会断但自动重连，用户无感。
15. 现有 SSE **没有 `id:` 字段** → 断线期间推送会丢。**但不用加 `id:`**，有更简单的解法：
    - **服务端已有去重**（`captureService.js:281` 返回 `outcome:'duplicate'`）→ **重发是安全的**
    - **抓取稳定性靠 APK 本地队列**：发送失败 → 本地存起来 → 下次连上补发
    - **SSE 只是"通知网页刷新"**，丢了不影响数据正确性 —— 批次落库，网页重连后拉「最近 N 批」即可补齐
    - ⚠️ **APK 侧目前似乎没有本地重试队列**（grep 未找到 retry/queue 逻辑）→ **这个要新增**
16. liveness 用**轮询 status**，不用「SSE 连着」判断 —— SSE 连着只说明浏览器↔服务器通，跟 APK 死活无关。
17. 空闲时段做**健康检查**（不只是心跳）：无障碍开着吗？cookie 还有效吗？QNI 在前台吗？
    → 让用户在**有空的时候**处理问题，而不是轮到唱歌才发现。

## 三、mapping（整个设计的核心）

18. `(游戏歌名, 游戏歌手) → { source, id }`，**source 三选一：local / qq / netease**。
19. **本地曲库不是捷径，它就是 source 之一**，曲库的歌**同样要 approve**。
20. **歌手是主键的一部分**，任何地方**不能只用歌名查**。
21. **平台侧歌手可以≠游戏侧歌手**（`凤凰传奇` vs `玲花/曾毅`）—— 这是常态。
    mapping 一旦建立，歌手对不对**完全不影响播放**。
22. **一个游戏歌曲只存一个 id**，**不做自动降级**，source 是什么走什么。
23. 已 approve 的**永久锁定**，自动搜索不再覆盖、也不再重新搜索。
24. 查询链：mapping命中 → 导入池匹配 → 外部搜索（只有最后一步调 API）。
25. 导入池匹配分档：**强档(名+歌手全等)自动 approve**；中/弱档进待确认队列。
26. 审核页面三个 filter（**approve 后来源就不重要了，合并在一起**）：

    | filter | 内容 |
    |---|---|
    | **已确认** | 导入的 + 自然搜索的，approve 后都在这 |
    | **待确认** | 导入的中/弱档 + 自然搜索的候选 |
    | **未遇见** | 导入了但实战还没碰到 |

    来源（导入 / 自然搜索）作为一个**标签**显示，不再单独分 filter。
27. 「未遇见」= 导入了但实战还没碰到，是**覆盖率进度条**，不急着确认。
28. 普通用户**不做任何标记**，歌曲对不对由网站决定；approve 只有 admin + 指定用户。
29. 权限用 `canEditMapping` 布尔标志，**不新增角色**。后端必须校验，不能只靠「猜不到网址」。
30. 实战中 approve：在**展开的播放器**里，点其他候选**立刻切过去播**，approve 后**立刻全站生效**。
31. 批量导入 pipeline **只有站长本机跑**，dry-run 默认，**冲突逐条列出不能默默覆盖**。
32. ⚠️ 歌手名里可能**自带 `_`**（而 `_` 是项目里的分隔符），算法无法可靠区分 →
    可疑情况**强制降弱档**人工过；approve 过的歌手名记进「已知歌手名」表，以后直接认。

## 四、播放与流量

33. **一律不自动播放**，展开才解析。
34. 点开到出声：曲库 ~0.1s / QQ ~0.7s / 网易 ~1.2s（搜索已缓存的前提下）。
35. 变调需要 `decodeAudioData` 整首（3MB 约 1-2s）→「点开出声」和「点开能变调」不是一回事。
36. 审核页面试听：**不需要变调、不需要跳转**，最轻的 `<audio>` 即可；曲库试听用 Range 只传前 30 秒。
37. **流量归属**：

    | 来源 | 你的流量 |
    |---|---|
    | 本地曲库 | **3-5 MB/首**（一局100首 = 300-500MB）|
    | QQ / 网易 | **~0**（音频走平台 CDN，服务器只出解析请求 1.8KB/首）|

38. **规则：一律优先外部，只有 approve 成 `source:"local"` 的个别歌走曲库。**
39. **用户必须配 cookie**（不用曲库兜底）→ cookie 有效性成为**硬前提**。
40. **缓存分两层，区别是「歌的身份」vs「播放凭证」**：

    | 缓存什么 | 例子 | 时长 | 能否跨用户 |
    |---|---|---|---|
    | **歌的身份**（搜索结果/歌词）| `(致青春,王菲) → mid` | **永久** | ✅ **可以** |
    | **播放凭证**（播放 URL）| `mid → https://...vkey=xxx&uin=xxx` | **20-30分钟** | ❌ **绝对不行** |

    - 为什么永久：mid 不会变、歌词是客观事实、**不含任何人的身份**
    - 为什么 20-30 分钟：**平台返回的播放 URL 自带时效签名**，几十分钟后自动失效。
      缓存它是为了「同一用户重复听同一首不用再解析一次」；
      设成比实际过期时间**略短**，避免拿到已失效的 URL
41. ⚠️ **播放 URL 绝不能跨用户共享** —— URL 内含 `uin`（用户身份），
    给别人用 = 变相共用账号 = 封号场景（有真实先例）。
41b. **网站已有「每用户流量统计」功能** → 可直接用真实数据验证第37条的流量对比，
    并且能看出：唱卡实际增加了多少流量、哪个用户的歌大多走曲库（= mapping 没配好）。

## 五、cookie（硬前提）

42. **cookie 只有 3 天** —— 你记得没错，cookie 自带时间戳证实（签发→过期正好 3 天）。
43. **‼️ 能否自动续期取决于「凭证怎么拿到的」，不是 QQ/微信**：
    - **手动粘 cookie → 拿不到 `refresh_key` → 3 天一换**
    - **扫码登录 → 凭证含 `refresh_key` → QQ 和微信都能自动续期**
    - → **扫码登录不只是方便，它是自动续期的前提。**
44. 续期接口是 `music.login.LoginServer/Login`（不是 `QQConnectLogin/QQLogin`，我一开始用错了）。
45. 扫码三选一，**推荐微信扫码**：3 步、纯 HTTP、不用 MQTT、国内覆盖面最广。
46. 过期检测用官方接口 `music.UserInfo.userInfoServer/GetLoginUserInfo`，`code != 0` 即过期。
47. 过期提醒分级：>24h 静默 / 6-24h 黄条 / <6h 红条 / 已过期阻断。
    **必须实测而非只读时间戳**（可能被顶下线或风控）。
48. 落地顺序：**先做手动粘贴**（确定能跑通），扫码列第二阶段（涉及腾讯登录体系，变动风险更高）。

## 六、风控（最大的长期隐患）

49. **我今天亲手把这台机器的 IP 打进风控两次。**
    症状：`104009` + `sip:[]`，持续数小时。
50. **判定方法：用匿名请求打同一接口。**
    匿名与带 cookie **症状相同 = IP/接口层问题**，别去折腾 cookie 和参数。
51. 风控是**按接口粒度**的 —— vkey 挂了，歌单/登录/搜索照常。
52. 触发原因：高频连续调同一接口、失败立即重试、请求间隔太规律。
53. **红线三条**：❌批量预热整个歌单 ❌失败后自动重试循环 ❌定时后台任务。
54. **必须加熔断器**：连续 N 次 `104009`/`104604` → **停止所有解析 15-30 分钟**。
    继续重试只会延长封禁。**今天就是缺这个，从「试几次」变成「封几小时」。**
55. `104604` = 官方的「操作过于频繁」错误码，可用于**精确触发**熔断。
56. 架构隐患：**所有用户共用服务器一个 IP**。最有效的缓解是 **mapping 表**（命中就不调 API）。
57. 限流：普通用户 30次/分，`canEditMapping` 更宽松。**危险的不是频率，是模式**
    （人工操作不规律=正常；脚本批量刷=异常）。

## 七、解析放哪执行

58. **先做服务器解析**，D 方案（APK 本机解析）留作第二阶段。
59. 理由：日志在服务器上适合前期 debug；前期未知数多，改一行重新部署就能观察。
60. D 的最大成本**不是技术难度，是长期维护** —— 等于把音源服务在 Android 上重写一遍，
    接口一变要**同时改两边 + 全员升级 APK**。
61. **现在就要做的准备**：解析写成**独立模块** `(平台, songId, cookie) → URL`，
    将来挪到 APK 只是换执行位置。
62. 实测：**模拟器网络开销只有 200-250ms**，不是秒级。
    模拟器慢在 **CPU（ARM 翻译层 libhoudini）**，不慢在网络。

## 八、过渡策略

63. **整个项目做成纯新增，过渡期不改歌P的短码。**
64. → 自动打标**一行代码都不用动**，新旧 APK 各走各的路，不需要协调升级时机。
64b. **旧歌P的退役要等到全部验证没问题之后**，分三阶段、**每阶段之间留观察期、不设时间表**：

    ```
    阶段1  新唱卡上线，歌P完全不动
    阶段2  新歌P连接方式上线，与短码并存
    阶段3  确认没问题后，才退役短码
    ```
65. 网页短码框用**做法 B**：主界面是新的，底下留一行小字「使用旧版客户端？点这里输短码」。
66. 服务端**只加字段、只加路由，永不删旧的** —— 旧 APK 收到多余字段会忽略，不会崩。
67. 上线顺序：`mapping表 → 音源模块 → 导入脚本 → 审核页 → cookie/扫码 → /live+新APK`。
    **前 4 步完全不碰现有功能。**
68. 新功能用 entitlement 门控（与自动打标同 package），出问题可关开关而不必回滚部署。

## 九、⚠️ 我今天犯的错（实现时警惕同类）

69. **说 `captureMatchService` 有「共用风险」——** 凭印象推断，没读文件。
    实读后：**它只 match 歌名，完全不碰歌手**。歌名能力可直接复用；
    歌手匹配写**新文件**；真正的风险只剩「别改 `normTitle` 的行为」。
70. **说「微信登录不能续期」——** 基于一次失败测试就下结论，**错的**。
    正确答案在一份 444★ 还在维护的开源实现里（用错了接口）。
71. **讲了一大堆 Android 保活/Doze/okhttp-eventsource ——** 前提就是错的，
    因为**没先去读现有 APK 是怎么连的**（它是短连接 POST）。
72. **把「用户说的用量估计」当成了「技术限流阈值」——**
    你说「每分钟不超过10首」是在描述场景，我写成了限流 10次/分。
73. **早上高频试参数把 IP 打进风控 ——** 而且**这是第二次**，笔记里明明记着上次的教训。
74. **共同教训**：
    - 动线上共用代码前**先实读**，别凭记忆
    - **单次探测失败 ≠ 全局结论**（先用匿名请求区分 IP 层 vs 凭证层）
    - **先读能跑通的开源实现**，别拿真实凭证反复试参数

## 十、遗留待验证（不阻塞开工）
